# Next research experiments: evaluator transfer and learner/allocation decisions

**Status:** prospective implementation protocol, written 29 September 2026. No results from the experiments below exist yet. Freeze a versioned config and its source hash **before** generating the new simulation seeds or evaluating a new domain. A post-result change starts a new exploratory protocol; it cannot repair the original gate retrospectively.

## Why these two studies

The [fresh evaluator diagnostic](../reports/v4/fresh_evaluator/FRESH_EVALUATOR_REPORT.md) covered six constructed independent-unit conditions, but its interval was selected after earlier results. The [asymmetry transfer study](../reports/v4/asymmetry_transfer/ASYMMETRY_TRANSFER.md) falsified its registered transfer predictions. Existing [Hillstrom development screening](../reports/v4/screening_reproduction/SCREENING_REPORT.md) ranks M01 first on Mens, while the Womens and [Lenta](../reports/v4/replication_lenta/EXTERNAL_REPLICATION.md) results differ. The [R04 factorial](../reports/v4/factorial/FACTORIAL_REPORT.md) shows an allocator null case with homogeneous costs and only assumed, heterogeneous prices. These are reasons to test **decision and inference domains**, not to search for a larger winning model zoo.

| Study | Frozen question | Output role |
|---|---|---|
| R1, evaluator transfer | Does the already selected paired DR interval cover a *fixed* policy on a new independent-unit generator, and does a separately specified reallocation or cluster interval cover its own batch/cluster estimand? | Known-truth synthetic validation; never a real business effect. |
| R4, learner comparison | With the same folds, input information, and contact envelope, does selecting among three prespecified causal learners improve held-out conversion value over fixed M01 enough to justify added fitting cost? | Development only on public randomized datasets. |
| R4, allocation comparison | With identical frozen scores and constraints, does an exact small-batch solver improve known-truth net value over the feasible rank rule when costs vary? | Synthetic, conditional on declared costs; no real ROI. |

## R1 — evaluator transfer

### Frozen design and estimands

Create a third generator, distinct from the inspected smooth and piecewise families. For each independent customer draw `X1, X2 ~ Bernoulli(0.5)`, `X3 ~ Uniform(-1,1)`. Use adverse-event risk `p0 = 0.002 + 0.025 sigmoid(1.2 X3 + 0.7 X1 - 0.5 X2)`. In effect cells set prevented-event effect `tau = 0.004 X1 - 0.002 X2`; in sharp-null cells set `tau = 0`. Draw `Y(a) ~ Bernoulli(p0 - a tau)` and reward `R = 1 - Y`. The generator must reject any probability outside `[0,1]`; it must not clip silently. Provide oracle `E[R(a)|X]` and logged propensity to the evaluator so this study isolates interval behavior from nuisance fitting. A separate learned-nuisance sensitivity may be run **after** the primary readout and labeled exploratory.

For fixed-rule cells, contact when `X1 = 1` and `X3 > 0`; the comparator contacts nobody. The target is that fixed rule's population reward contrast. For batch cells, rank by `X1 + 0.1 X3`, break ties by stable customer ID, and contact at most `floor(0.20N)` per independently drawn batch. The target is expected value over *new batches*, not the conditional value of the observed feature frame. Establish reference truth with an independently seeded large Monte Carlo run and report its MC standard error. If truth MCSE exceeds one tenth of the median reported CI half-width, increase truth simulation before reading coverage or mark the cell invalid.

Use 4,000 rows per world and **2,000 unseen worlds per cell**. Register the RNG seed namespace and code hash before the first main world; the old F01–F06 seed and outcomes cannot serve as the unseen set. The following six cells are the complete primary matrix, rather than the Cartesian product of every factor:

| Cell | Population / rule | Effect | Assignment | Intended inference |
|---|---|---|---|---|
| T1 | Independent customers; fixed rule | Null | `e(X)=0.15+0.70 sigmoid(X3)` | Selected `skewness_adjusted_t`, effective df floor 1; normal paired DR reference. |
| T2 | Independent customers; fixed rule; all event probabilities and `tau` multiplied by 0.25 | Heterogeneous | Same variable `e(X)` | Same as T1; rare-event stress. |
| T3 | Independent customers; 20% hard batch cap | Null | Constant `e=0.85` | Paired reallocation bootstrap; selected fixed-rule interval only as an explicitly out-of-domain diagnostic. |
| T4 | Independent customers; 20% hard batch cap; rare-event scaling as T2 | Heterogeneous | Variable `e(X)` | Paired reallocation bootstrap. |
| T5 | Two records per customer, shared customer intercept and customer-level assignment; 20% cap on unique customers | Null | Cluster-level `e=0.50` | Customer-cluster reallocation bootstrap; naive row-IID interval is a negative control. |
| T6 | Same clustered design as T5 | Heterogeneous | Cluster-level `e=0.50` | Customer-cluster reallocation bootstrap. |

For T5–T6, draw one shared intercept `U_customer ~ Uniform(-0.7,0.7)` per customer and replace the sigmoid argument in `p0` with `1.2 X3 + 0.7 X1 - 0.5 X2 + U_customer`; store the intercept only inside the generator and oracle nuisance. This bounded range keeps `p0 - tau` positive for every declared feature combination. Draw the two outcomes independently conditional on this intercept. Both records inherit the same pre-treatment customer features and action; contact cost and capacity count **customers**, not records. Compute a customer-level mean reward before policy evaluation. Resample whole customers, preserve duplicate occurrences with distinct bootstrap IDs, and rerun both policies' batch allocations within every resample. The current `paired_contrast(..., interval_method="skewness_adjusted_t")` [rejects declared clusters](../src/telco_churn/policy_comparison.py); a refusal is correct behavior, not a missing score to impute. The existing cluster `bootstrap_t` handles fixed action arrays; batch reallocation is an additional method to implement and validate, not an existing capability to claim.

### Readouts, controls, and stop rule

For every cell, report true contrast, point-estimate bias, empirical 95% coverage with 95% Wilson bounds, interval width, Monte Carlo error, positive-lower-bound promotion rate, design support, effective independent units, and any failed interval calculation. Compare against the declared normal paired DR reference only in its supported independent fixed-rule cells. T1, T3, and T5 are sharp-null false-promotion cells. Add three deliberately broken controls, reported separately from candidate coverage: wrong logged propensity, row-IID resampling of T5 clusters, and evaluation-outcome leakage into policy ranking. These must be detected by provenance/role checks or show their expected known-truth failure; they cannot become promoted methods.

Before running, compute and archive the familywise false-*gate*-failure probability for the actual number of cells and nominal Monte Carlo design. A supported cell passes only if its coverage Wilson lower bound is at least `0.92`; a null cell additionally requires the false-promotion Wilson upper bound at most `0.05`. All six cells and every failure remain visible. A method is licensed only for its passing, implemented estimand/design combination. If a gate fails, stop promotion and narrow its stated domain; do not change the interval, seed, bootstrap scheme, or cell set and call the rerun independent confirmation. Even passing all six would validate these synthetic conditions only. Causal confirmation remains unmet; no uplift or ROI claim follows. The evidence index may independently classify the reproducible software as an engineering foundation.

## R4 — bounded learner comparison

Use the existing public, randomized **development roles only**: Hillstrom Mens versus no email, Hillstrom Womens versus no email as a sensitivity branch, and Lenta SMS development as a separate domain. Do not force one schema, channel, or outcome definition onto another. Use three shared outer folds with train-only preprocessing and the same data rows for every candidate. Inside each outer train portion, use three inner folds if choosing among candidates or settings. Do not use the outer evaluation outcomes for refitting, nuisance tuning, threshold selection, or choosing the winning report.

Freeze four recipes from the [runbook](archive/EXPERIMENT_RUNBOOK_V4.md): M01 control-outcome Logistic (`C=0.3`, natural prevalence) as fixed comparator; M03 S-Logistic (`C=0.3`); M05 T-Logistic (two arm models, each `C=0.3`); M07 cross-fitted DR-Ridge (`alpha=10`, common nuisance recipe). No hyperparameter grid, extra family, or model-specific feature set enters this run. Share folds, feature contract, supported actions, and evaluator nuisances; measure internal fits and CPU time rather than comparing only top-level fit counts.

**Primary development procedure:** inner-fold estimated whole-cohort policy value chooses one of M03/M05/M07, with deterministic tie order M03, M05, M07; the winner is refit on that outer train portion, then compared with fixed M01 on the untouched outer fold. Use a 20% hard contact cap for every candidate. Report the three outer paired deltas in conversions per 1,000 eligible customers, an event/support table, disagreement fraction, compute cost, and each domain separately. Report no-contact policy value as a safety reference. Use **one extra conversion per 1,000 eligible customers** as an explicit *development-priority* margin, not a business profitability threshold. The three-fold spread describes development instability; it is **not** a population confidence interval or a hypothesis test. Report M03/M05/M07 individual values as secondary diagnostics, including failed fits; if a candidate fails a required fold, mark it incomplete instead of averaging the surviving folds.

Because all these public domains have already been inspected, this run can refine the selection procedure but cannot establish a new generalization claim. Before any later one-use confirmation, require (a) a stable fixed recipe or independently justified rule, (b) a domain-appropriate validated batch evaluator from R1, (c) a **new** external-domain replication under the *same* frozen protocol, and (d) a signed R09 manifest with one primary contrast and a practical margin. Do not open Hillstrom confirmation merely because the development mean is positive. If the development mean does not clear the planning margin or the selected recipe changes across folds/domains, retain M01 for this scope and report the instability. Clearing it only prioritizes further study.

## R4 — allocation comparison under equal constraints

Use **new known-truth synthetic worlds**, not Hillstrom's assumed channel prices, for the primary allocator claim. Freeze one M07 score recipe before worlds are generated. In each world, fit on 10,000 units, use 5,000 distinct units for any permitted training-side selection, and evaluate 50 independent batches of 20 eligible units each. Draw 30 new worlds for each of three prespecified mechanisms: benefit aligned with baseline risk, benefit opposed to it, and a sharp-null/negative-control mechanism. Use the [R04 mock generator](archive/EXPERIMENT_RUNBOOK_V4.md) as the starting feature/outcome contract and record any necessary new small-batch/cost revision **before** running these worlds. The 90 worlds, not the 4,500 batches, are the independent units for cross-world uncertainty.

Compare (A) feasible rank-by-predicted-**net**-proxy with skip-if-cost-does-not-fit against (B) an exact dynamic-programming or exhaustive small-batch solver maximizing the **same** predicted net proxy. Each batch has a maximum of `floor(0.20×20)=4` contacts, at most one action per customer, a money cap of **2 currency units**, assumed value **100 currency units per prevented event**, and assumed contact cost **0.2 when `X2=0`, 1.2 when `X2=1`**. Do not change these values after seeing evaluation outcomes. Both policies may choose nobody. Check exact optimality against brute force on a few tiny batches as an algorithm property, not as a substitute for the 90-world value study. Keep homogeneous-cost, zero-money-cap, all-negative-value, ties, and infeasible-action cases as named mechanical controls.

Primary contrast is the **paired true expected net proxy per 1,000 eligible units**, B minus A, under the same realized worlds and actual generator probabilities. Give its 95% interval from independent-world paired differences, alongside MCSE, disagreement, capacity/cost violations, unused capacity, solver gap (zero if exact), and runtime. Report each mechanism separately and any average only as secondary. The predeclared practical gain is **1 synthetic currency unit per 1,000 eligible customers** in the opposed-benefit mechanism, where constrained cost selection is expected to matter; this is a methodological threshold, not a partner business margin. Carry the exact solver forward only if that mechanism's lower interval bound exceeds this margin and it has zero constraint violations; otherwise retain the simple rank rule or mark the comparison inconclusive. The null mechanism must not be promoted as a gain. A better predicted objective without better held-out true value is a negative result, not a deployment win.

## Compute and execution decision

First implement the two runners and produce a dry-run manifest that checks schemas, role isolation, resource estimates, and planned cells **without reading evaluation outcomes**. Then run one complete protocol at its declared size; do not accumulate many tiny tests and promote a convenient one. R1 has six times 2,000 generated worlds and no learner fits. R4 learner work is at most four recipes across three outer folds per domain plus bounded inner selection; R4 allocation has 90 independent worlds and an exact solver only on batches of 20. Profile a handful of *training-side* iterations solely to estimate wall time, then either run the frozen plan on CPU or revise the plan before main outcomes are seen. Existing tabular models and simulation do not require GPU. If profiling shows a genuine GPU benefit, prepare a Kaggle package with pinned dependencies, source/data hashes, offline inputs or verified fetch steps, a CPU baseline, role-safe output paths, and the same config and stopping rules; GPU availability alone does not justify changing the scientific question.

**Deliverables:** frozen configs and manifests, a machine-readable per-cell result, one concise report per study, negative-control results, failure ledger, CPU time and reproducibility hashes, and an update to the [evidence index](../reports/v4/EVIDENCE_INDEX.md). Report the computed engineering tier separately from causal evidence. Causal confirmation remains unmet; the planner's value figures are assumptions, and no measured uplift or ROI may be claimed without new evidence.
