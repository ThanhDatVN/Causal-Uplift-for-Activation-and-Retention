## Phase 1 — reproducibility and truthful release signals (P0, 2–4 working days)

1. Check out the project into an empty directory on Linux and Windows, install Python 3.11 dependencies, fetch the checksum-verified IBM file, run `--quick`, build the wheel, start the API, and replay a fictional packet. Record commands, elapsed time, environment, hashes, and failures in a dated verification artifact. Repeat the final full Python suite after the model-hash change. If the Monte Carlo portion is too slow for pull requests, identify those tests explicitly and run them as a required scheduled or release gate; keep a fast pull-request suite and publish both results. Do not silently remove tests.
2. Observe a real GitHub Actions run from a repository checkout and fix any failures. A workflow file alone is not a green CI result. Add a status badge only after the run is visible; [GitHub's workflow documentation](https://docs.github.com/en/actions/how-tos/monitor-workflows/add-a-status-badge) explains what the badge represents.
3. Create one machine-readable artifact manifest for each new run: source revision, command, data checksum, split checksum, environment-lock result, model checksum, metric report checksum, protocol version, UTC time, and `development`/`confirmation`/`synthetic` role. Label old reports whose producer revision cannot be reconstructed as **archived**.

**Exit:** a stranger can follow the [release guide](PORTFOLIO_RELEASE_2026_EN.md) from a clean checkout; the final revision has a completed full-suite or explicitly split fast/slow gate; hosted CI is observed; all visible numbers point to a role-labeled artifact. A quick run must not replace the archived full benchmark.

1. Exercise the planner in Chromium and one second browser at desktop and narrow mobile widths. Complete the full demo, invalid CSV, duplicate ID, missing optional history, zero-contact, zero-money, model-unavailable, download, and replay flows. Keep screenshots and a short defect log. Use [W3C form guidance](https://www.w3.org/WAI/tutorials/forms/) and [WCAG error identification](https://www.w3.org/WAI/WCAG22/Understanding/error-identification) as the acceptance reference.
2. Add a data preview before scoring: detected row count, required/optional column status, first few fictional or approved rows, and concrete line/field errors. The browser should never send invalid rows silently. Keep the raw file local until the user previews; the API remains localhost-only for this portfolio release.
3. Run five first-time-user sessions with the [prepared study script](USABILITY_SESSION_PROTOCOL_EN.md): load fictional data, set capacity/cooldown, explain why a customer was skipped, export and replay, and state whether the displayed value is measured ROI. Record completion time, errors, and interpretations. Revise wording and layout once, then repeat the failed tasks. Five sessions are a small usability check, not statistical proof.
4. Update [model](MODEL_CARD.md) and [data](DATA_CARD.md) cards with the current model digest, static-sample scope, legacy API field name, and export sensitivity. Add an immutable artifact ID or digest to every report and define a compatible path to rename `risk_30d` without breaking existing clients.

**Exit:** all scripted browser flows pass; a keyboard user can complete the demo; at least four of five first-time users finish it within five minutes; none of those five describes scenario value as measured uplift or ROI. If the sample reveals confusion, change the product and rerun that task rather than claiming success.

## Conditional work outside the portfolio release

**Partner pilot:** requires a time-stamped eligible population, consent rules, randomized action/control assignment with known probabilities, delivered-action logs, actual cost ledger, mature outcomes, a human approval path, monitoring, and rollback. Preregister the estimand, policy cap, interval, and launch gate before assigning customers. The current public datasets cannot supply these fields, so the project must not claim measured telecom uplift or ROI while this dependency is absent.

**AI assistant:** implement only if a fixed evaluation set shows that a simple cited template is insufficient. Any retrieval or generation must be limited to versioned local evidence, quote source IDs, refuse unsupported causal claims, and pass adversarial and missing-evidence questions. It is optional for a junior AI Engineer portfolio; it must not change the deterministic decision or evidence gate.

**Kaggle/GPU:** do not add a GPU notebook simply to show GPU use. The present tabular baselines, replay, and evaluator run on CPU. In response to the requested compute handoff, a [Kaggle CPU bundle](../kaggle/README.md) now packages the unrun full-development Lenta nested comparison with input hashes, the completed 60k CPU reference, fixed seeds, an output schema, and a return verifier. This is a prepared extension, not an executed result or proof that the laptop cannot run it. A GPU-capable challenger would require a separate frozen protocol and measured reason to use an accelerator.
